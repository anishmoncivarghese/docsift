# DocSift v0.1 Specification — CLI release

**Source of truth:** [DocSift PRD v0.2](../../../DocSift_PRD_v0.2.md). This spec distills the PRD sections that apply to release v0.1 (Milestones 0–3). Anything not listed here is out of scope for v0.1.

## What v0.1 is

A locally installed command-line tool and Python library that converts a document into clean, structured, AI-ready Markdown plus a normalized JSON result — with token-aware chunks, token estimates, and caching. No server, no API, no search.

```text
docsift convert report.pdf
→ output/report.md
→ output/report.docsift.json   (normalized result: metadata, metrics, chunks, warnings)
```

## Functional requirements in v0.1 (from PRD §11)

- **FR-01 Ingestion:** local file path via CLI. PDF is the required format; MarkItDown-supported formats (DOCX, PPTX, XLSX, HTML, CSV, JSON, XML, ZIP, EPUB, TXT, MD) are accepted best-effort.
- **FR-02 Validation:** file exists, non-empty, supported extension, ≤ 50 MB default. (MIME sniffing, password/corruption detection: M2+.)
- **FR-03 Engine selection:** `auto` | `docling` | `markitdown`; selected engine **and reason** recorded in the result.
- **FR-04 Conversion:** normalized Markdown out, via the common schema.
- **FR-05 Fallback:** on auto-mode primary failure, optionally try the alternate engine, preserving both engines' warnings. (M2.)
- **FR-06 Cleaning:** whitespace normalization, repeated header/footer removal, page-number removal, page markers as HTML comments `<!-- page: N -->`. (M3.)
- **FR-07 Chunking:** heading-aware, token-capped, configurable overlap, tables kept intact (oversized tables split by rows with repeated header), stable chunk IDs, section path + page metadata. (M3.)
- **FR-08 Token estimation:** `o200k_base` via tiktoken with character-ratio fallback; counts for raw output, cleaned Markdown, each chunk, whole document. (M1 ships the fallback estimator; tiktoken lands in M3.)
- **FR-09 Caching:** cache key = source SHA-256 + config + engine version + DocSift version. (M3.)
- **FR-12 CLI:** `convert`, `inspect`, `compare` (M2), `--engine`, `--output`, `--version`.
- **FR-14 Comparison mode:** both engines on one document, machine-readable metrics. (M2.)

## Normalized result schema (PRD §10)

Pydantic models, engine-neutral, JSON-serializable:

- `SourceMetadata` — filename, media_type, size_bytes, sha256
- `ConversionMetadata` — engine, engine_version, docsift_version, selection_reason, started_at, completed_at, duration_ms, ocr_used, cached
- `DocumentContent` — title, page_count, language, markdown
- `ConversionMetrics` — characters, words, estimated_tokens
- `ConversionWarning` — code, message
- `Chunk` — chunk_id, text, estimated_tokens, section_path, pages (populated from M3)
- `ConversionResult` — document_id (`doc_` + first 12 hex of sha256), source, conversion, document, chunks, metrics, warnings

## Engine rules (PRD §9)

- PDF → **Docling**, always. No complexity detection — ever (PRD non-goal 11).
- Non-PDF supported formats → **MarkItDown**.
- MarkItDown may convert PDFs only via explicit `--engine markitdown` or in compare mode.
- Both engines implement one `ConversionEngine` interface; engine-specific imports and types never leave `engines/`.
- Engine imports are lazy: the CLI must start when neither engine is installed, failing with a clear install hint only when an unavailable engine is actually requested.

## Non-functional requirements in v0.1

- Python 3.11/3.12, macOS + Windows + Linux, CPU-only (NFR-01).
- Simple 20-page digital PDF < 30 s on a modern laptop (NFR-02, engineering target).
- Engine failure returns a structured error, never a crash; original file never modified (NFR-03).
- No document contents in logs (NFR-05 / FR-16).
- Both engines behind one adapter interface; versions pinned via `uv.lock`; Ruff + pytest + type checks in CI (NFR-06).

## v0.1 acceptance criteria (PRD §16)

1. Installable locally from PyPI.
2. Convert a PDF with Docling.
3. Convert a PDF with MarkItDown (explicit selection).
4. Engine choice: explicit or auto.
5. Both engines return the same normalized structure.
6. Cleaned Markdown produced.
7. Token-aware chunks produced.
8. Token estimates produced.
9. Unchanged documents served from cache.
10. CLI supports conversion and comparison.
11. No paid API required.
12. Tests and CI pass.

## Explicitly out of scope for v0.1

REST API, async jobs, storage service, SQLite, search, n8n/Copilot Studio integrations, MCP server, web UI, vector search, OCR quality guarantees, handwritten documents.
